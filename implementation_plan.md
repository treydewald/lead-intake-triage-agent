Feature 01: Pipeline Orchestration Layer

Tier: Tier 1

Execution Metadata (REQUIRED)
status: COMPLETED
group: FOUNDATION
locked: false
assigned_worker: null
is_blocked: false
depends_on: []

Description
The state-machine backbone (LangGraph or an equivalent lightweight orchestrator) that coordinates
the six downstream pipeline stages (Intake Parsing, Intent Classification, Data Enrichment, HubSpot
CRM Write, Human Review & Approval Gate, Outcome Notification) as genuinely separate units — each
with its own scoped tool access and its own piece of state — rather than one large prompt. This is
the architectural foundation every other Tier 1 feature plugs into, and the single feature the
project definition's Critical risk (the per-stage tool/state boundary must be real under code
inspection, not cosmetic) attaches to directly. Everything downstream depends on this existing and
enforcing scoping before any stage logic is written.

Requirements

Functional Requirements:
- Define a Stage interface/contract (input schema, output schema, allowed tool set, state slice) that
  every pipeline stage implements
- Wire a state-machine graph connecting stages in the core workflow order: Intake Parsing → Intent
  Classification → Data Enrichment → HubSpot CRM Write, with a conditional branch to Human Review
- Enforce per-stage tool-access scoping in code (e.g. each stage receives only the tool bindings it's
  permitted, not a shared unrestricted toolset) — not documentation-only
- Define the shared lead-record state schema that flows through the graph, with each stage
  reading/writing only its declared slice
- Implement stage transition logic (success → next stage, failure → error state, low-confidence →
  Human Review branch)
- Implement error handling: a stage failure halts the pipeline for that lead and records the failure
  in state rather than silently continuing

System Behaviors:
- Each stage is invoked with only the state fields and tools declared in its contract
- A stage cannot call another stage's scoped tool (e.g. Intent Classification cannot call the HubSpot
  write tool) — attempting to do so raises an error the orchestrator catches and logs, not a silent
  no-op
- Stage transitions are deterministic given the current state and the current stage's output
- Pipeline execution for one lead is independent of any other lead's execution (no shared mutable
  state across leads)

Edge Cases:
- **Stage throws an unhandled exception:** Orchestrator catches it, marks the lead's pipeline run as
  FAILED with the stage name and error, does not proceed to the next stage
- **Stage attempts an out-of-scope tool call:** Rejected at the binding layer, logged as a boundary
  violation (this is the condition the project's Critical risk is meant to catch)
- **Malformed state passed between stages:** Schema validation failure halts the transition and
  records a validation error, rather than passing partial/invalid state forward
- **Duplicate pipeline invocation for the same lead (e.g. retry):** Orchestrator must not double-run
  side-effecting stages without idempotency support from the stage itself (see Feature 05)

Inputs
- A raw lead-record trigger event (from Feature 02's entry point) that starts a pipeline run
- Stage contract definitions (code-level, not runtime input)

Outputs
- A running/completed/failed pipeline-run state object, keyed per lead, containing each stage's
  recorded output as it completes
- Structured trace entries per stage transition (consumed by Feature 08)

Acceptance Criteria
- [x] A stage cannot access state fields or tools outside its declared contract, verified by a test
  that attempts an out-of-scope call and asserts it is rejected
- [x] The graph correctly routes a high-confidence lead through Intake → Classify → Enrich → CRM
  Write → Notify with no Human Review branch taken
- [x] The graph correctly routes a low-confidence lead into the Human Review branch instead of
  auto-proceeding to CRM Write
- [x] A stage exception halts that lead's pipeline run and is recorded, without affecting other
  leads' concurrent runs
- [x] Every stage transition is captured in a form Feature 08 can query per lead

Feature 02: Intake Parsing & Normalization Stage

Tier: Tier 1

Execution Metadata (REQUIRED)
status: COMPLETED
group: PIPELINE_STAGES
locked: false
assigned_worker: null
is_blocked: false
depends_on: [01]

Description
Normalizes a raw inbound lead — a web form submission, email text, or missed-call callback
transcript — into the structured lead record the rest of the pipeline consumes. This is the first
real data to enter the pipeline and the stage every other pipeline stage's input schema depends on.

Requirements

Functional Requirements:
- Accept a web-form submission payload (structured fields: name, phone, email, message) and map it
  directly into the structured lead-record schema
- Accept raw email text and extract available structured fields (sender name/email, subject, body)
  plus retain the unstructured message body for downstream classification
- Accept a missed-call callback transcript (plain text) and produce a structured record with
  whatever fields are extractable (caller phone number if present) plus the transcript as the
  unstructured message body
- Normalize field formatting (phone number format, email casing/whitespace trim) consistently across
  all three channels
- Tag every normalized record with its source channel (web_form / email / callback)
- Emit the normalized record into the orchestrator (Feature 01) as the pipeline-run trigger

System Behaviors:
- Fields not present in the raw input are left explicitly null/missing in the structured record,
  never guessed or fabricated at this stage (enrichment is Feature 04's job, not this stage's)
- This stage has no external tool access beyond parsing/normalization logic — it does not call the
  CRM, LLM classification, or enrichment lookups
- Output conforms exactly to the shared lead-record schema Feature 01 defines

Edge Cases:
- **Empty or whitespace-only message body:** Record is still created with an explicit
  empty-message flag so downstream classification can handle it as low-signal rather than crashing
- **Missing required identifying field (no name, no phone, no email) across all channels:** Record is
  still created and flagged as low-identifiability; not rejected outright, since Data Enrichment may
  later resolve it
- **Malformed email (unparseable structure):** Falls back to treating the entire raw text as the
  unstructured message body with all structured fields null
- **Duplicate submission of the same raw payload (e.g. form double-submit):** This stage does not
  dedupe — dedup/idempotency is enforced at the CRM write stage (Feature 05), not here

Inputs
- Web form submission (structured JSON/form payload)
- Raw email text (plain text or MIME-parsed body)
- Missed-call callback transcript (plain text)

Outputs
- A structured lead record: {source_channel, name, phone, email, message_body, raw_input_ref,
  received_at}, handed to Feature 01's orchestrator as the pipeline trigger

Acceptance Criteria
- [x] A web-form payload with all fields present produces a fully-populated structured record
- [x] Raw email text produces a record with extracted sender fields and the full body retained
- [x] A callback transcript with no extractable structured fields still produces a valid record with
  the transcript as message_body
- [x] Every normalized record is tagged with the correct source_channel
- [x] An empty message body does not crash normalization and is explicitly flagged

Feature 03: Intent Classification Stage

Tier: Tier 1

Execution Metadata (REQUIRED)
status: COMPLETED
group: PIPELINE_STAGES
locked: false
assigned_worker: null
is_blocked: false
depends_on: [01, 02]

Description
Classifies a normalized lead's intent/urgency (e.g. buyer vs. browser vs. spam) and produces a
confidence score. This stage is read-only-lookup-scoped — it may call the classification LLM and
read the lead record, but has no write access to the CRM or any other external system. Its output
(classification + confidence) is what both Data Enrichment ordering and the Human Review gate key
off downstream.

Requirements

Functional Requirements:
- Call a local open-weight LLM (via Ollama) with the normalized lead record to produce an intent
  classification from a fixed label set (e.g. buyer, browser, spam) plus a numeric confidence score
- Support an optional hosted-LLM-API fallback path, used only if local tool-calling proves
  insufficiently reliable (per the project's stated conditional exception — not invoked by default)
- Persist the classification result and confidence score into the lead record's classification slice
- Enforce read-only tool scoping for this stage: no CRM write access, no enrichment-lookup access

System Behaviors:
- Confidence score is a normalized numeric value (e.g. 0.0–1.0) usable by Feature 06's
  threshold-routing logic
- Classification is deterministic given the same input and model/version (repeatable for the
  benchmark in Feature 09)
- If the hosted-API fallback path is invoked, the result is tagged with which model produced it, so
  the benchmark report (Feature 09) can distinguish local vs. fallback results

Edge Cases:
- **Empty/low-signal message body (flagged by Feature 02):** Classify as low-confidence rather than
  guessing a high-confidence label
- **LLM call times out or errors:** Retry once; if it still fails, mark the lead's classification as
  FAILED and route to Human Review rather than blocking the pipeline indefinitely
- **Ambiguous message that plausibly matches multiple intent labels:** Confidence score should reflect
  the ambiguity (lower score), not force a single label at high confidence
- **Model returns a label outside the fixed label set:** Reject the response, retry once, then fail to
  Human Review if still invalid

Inputs
- Normalized lead record (from Feature 02, via Feature 01's state)

Outputs
- Classification result: {intent_label, confidence_score, model_used}, written into the lead record's
  classification slice for Feature 04 and Feature 06 to consume

Acceptance Criteria
- [x] A clearly buyer-intent message produces the buyer label with a high confidence score
- [x] An empty or near-empty message body produces a low-confidence result rather than an error
- [x] An LLM call failure results in a FAILED classification routed to Human Review, not a pipeline
  crash
- [x] Classification stage has no successful path to CRM-write or enrichment-lookup tools, verified
  by a boundary test
- [x] The same input produces the same classification label across repeated runs (deterministic
  enough for benchmarking)

Feature 04: Data Enrichment Stage

Tier: Tier 1

Execution Metadata (REQUIRED)
status: COMPLETED
group: PIPELINE_STAGES
locked: false
assigned_worker: null
is_blocked: false
depends_on: [01, 03]

Description
Fills missing lead fields (contact/context details) using external-lookup-scoped tools only. This
stage explicitly has no CRM-write access — it only reads external lookup sources and merges results
into the lead record — preserving the per-stage boundary between "gather more information" and
"commit information to the CRM" (Feature 05).

Requirements

Functional Requirements:
- Detect which fields on the lead record are missing after Intake Parsing (e.g. no email present, no
  name present)
- Call external-lookup tool(s) to attempt to fill missing fields (e.g. a lookup keyed on
  phone/email if available)
- Merge any successfully-resolved fields into the lead record without overwriting fields Intake
  Parsing already populated
- Enforce lookup-only tool scoping: this stage cannot call the HubSpot write tool under any
  condition

System Behaviors:
- Enrichment is best-effort — a field that cannot be resolved remains explicitly missing, not
  fabricated
- Enrichment results are tagged with their source (which lookup tool resolved them) for the
  observability trace
- This stage does not alter the classification result produced by Feature 03; it only adds/fills
  contact/context fields

Edge Cases:
- **No missing fields to enrich:** Stage completes as a no-op pass-through, still logging a trace
  entry
- **External lookup tool is unavailable/times out:** Stage does not fail the pipeline — it proceeds
  with fields left missing, and logs the lookup failure for observability
- **Lookup returns conflicting data vs. an already-present field:** Never overwrite an
  already-populated field; log the conflict for visibility rather than silently choosing one value
- **Lookup returns a low-confidence/fuzzy match:** Only merge fields above whatever the lookup tool's
  own match-confidence threshold requires; a fuzzy result should not be merged as fact

Inputs
- Lead record with classification result attached (from Feature 03, via Feature 01's state)

Outputs
- Enriched lead record with any resolved missing fields merged in, plus an enrichment trace entry
  (fields attempted, fields resolved, source) for Feature 08

Acceptance Criteria
- [x] A lead record missing an email field, where the lookup tool can resolve it, ends up with the
  email field populated and tagged with its source
- [x] A lead record with all fields already present passes through unchanged and still logs a trace
  entry
- [x] An external lookup timeout does not fail the pipeline run
- [x] Enrichment stage has no successful path to the HubSpot write tool, verified by a boundary test
- [x] An already-populated field is never overwritten by a conflicting lookup result

Feature 05: HubSpot CRM Write Stage

Tier: Tier 1

Execution Metadata (REQUIRED)
status: COMPLETED
group: CRM_INTEGRATION
locked: false
assigned_worker: Worker-1
is_blocked: false
depends_on: [01, 04]

Description
An exclusively CRM-write-scoped stage that performs an idempotent, retry-safe create/update against
HubSpot's real free-tier developer sandbox — real auth, real rate limits, not a mock. This is the
highest-risk external integration in the project and is built early per the project definition's own
guidance to verify sandbox behavior before the rest of the pipeline is finalized around it.

Requirements

Functional Requirements:
- Authenticate against a real HubSpot free-tier developer sandbox account using its API credentials
- Given an enriched lead record, look up whether a matching HubSpot contact/record already exists
  (dedupe lookup, e.g. by email or phone)
- If no match exists, create a new HubSpot contact record populated from the lead record's fields
- If a match exists, update the existing record rather than creating a duplicate
- Implement an idempotency mechanism (idempotency key or dedupe-lookup-before-write) so that a retried
  pipeline run for the same lead never produces a duplicate HubSpot record
- Implement retry-with-backoff for transient HubSpot API failures (rate limit responses, transient
  5xx errors)
- Enforce write-only tool scoping for this stage: no other stage may call HubSpot's write API directly

System Behaviors:
- A rate-limited response from HubSpot triggers backoff-and-retry, not an immediate failure
- A genuine write failure (after retries exhausted) marks the lead's pipeline run as FAILED at this
  stage rather than silently proceeding to Notification as if the write succeeded
- Every write attempt (success, retried, or failed) is logged with the HubSpot record ID (if any) for
  the observability trace

Edge Cases:
- **Same lead processed twice (pipeline retried after a downstream failure):** Second write must
  update the existing HubSpot record, never create a duplicate
- **HubSpot sandbox rate limit hit:** Backoff and retry per HubSpot's documented rate-limit headers,
  up to a bounded retry count
- **HubSpot sandbox auth token expired/invalid:** Fail this stage explicitly with an auth error,
  distinct from a data/validation error, so it's diagnosable in the trace
- **Partial field data (e.g. no email, only phone) attempting a dedupe lookup:** Fall back to
  whatever identifying field is available; if no reliable dedupe key exists, create a new record and
  flag the uncertainty in the trace rather than silently guessing a match

Inputs
- Enriched lead record (from Feature 04, via Feature 01's state)

Outputs
- HubSpot contact record ID (created or updated), write-result status (created / updated / failed),
  logged as a trace entry for Feature 08 and consumed by Feature 06's gate logic

Acceptance Criteria
- [x] A new lead with no existing HubSpot match creates exactly one HubSpot record
- [x] Re-running the same lead's pipeline (simulated retry) updates the existing record instead of
  creating a second one
- [x] A simulated HubSpot rate-limit response triggers backoff-and-retry rather than immediate failure
- [x] A write failure after retries are exhausted marks the pipeline run FAILED at this stage, not
  silently treated as success
- [x] No pipeline stage other than this one has a successful path to HubSpot's write API, verified by
  a boundary test

depends_on: [01, 03, 05]

Description
Routes low-confidence classifications to a human reviewer with the agent's draft classification
attached, instead of letting the pipeline auto-act on uncertain cases. High-confidence cases bypass
this gate entirely and proceed automatically to the CRM write stage. This is the core decision logic
that prevents the agent from silently guessing on ambiguous leads.

Requirements

Functional Requirements:
- Compare Feature 03's confidence score against a configurable threshold immediately after
  classification
- If confidence is at/above threshold: allow the pipeline to proceed automatically to Data
  Enrichment → CRM Write with no human step
- If confidence is below threshold: route the lead into a review queue instead of proceeding to CRM
  Write automatically, attaching the draft classification and confidence score
- Provide a reviewer action: approve (proceed to CRM Write as classified), reject (halt pipeline for
  this lead, no CRM write), or edit (reviewer supplies a corrected classification, then proceeds to
  CRM Write with the corrected value)
- On reviewer approval or edit, resume the pipeline from the point it was paused (i.e. proceed into
  Data Enrichment / CRM Write) rather than restarting the whole pipeline from Intake

System Behaviors:
- A lead sitting in the review queue is not auto-processed by any timeout or background job — it
  waits for an explicit reviewer action
- The review-queue data model persists which lead, which draft classification, and which stage the
  pipeline paused at
- Resume-on-approval reuses Feature 01's orchestrator resume mechanism rather than a separate ad hoc
  code path

Edge Cases:
- **Reviewer rejects the lead:** Pipeline halts for that lead with no HubSpot write and no further
  auto-action; this is a valid, terminal outcome, not an error state
- **Reviewer edits the classification to a different label:** The corrected label must be what
  Feature 05's CRM write reflects and what Feature 09's benchmark can compare against the original
  model output
- **Confidence score exactly equal to the threshold:** Defined explicitly as one side (e.g.
  >= threshold auto-proceeds) so behavior is deterministic, not ambiguous
- **Multiple reviewers act on the same queued lead concurrently:** Only the first action is applied;
  the second is rejected with a "already actioned" response, not silently overwritten

Inputs
- Lead record with classification result and confidence score (from Feature 03)
- Reviewer action (approve / reject / edit) via the review-queue UI, once queued

Outputs
- Either: an unmodified pass-through signal to Feature 01 (high-confidence case), or a queued
  review-item record; after reviewer action, a resume signal (with original or corrected
  classification) back into the orchestrator

Acceptance Criteria
- [ ] A high-confidence lead proceeds automatically through to CRM Write with no queue entry created
- [ ] A low-confidence lead is queued for review and does not reach CRM Write until a reviewer acts
- [ ] Reviewer approval resumes the pipeline into CRM Write using the original classification
- [ ] Reviewer edit resumes the pipeline into CRM Write using the corrected classification
- [ ] Reviewer rejection halts the pipeline for that lead with no CRM write performed
- [ ] A second concurrent action on an already-actioned queue item is rejected, not applied
